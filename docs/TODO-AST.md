           Lezer
Lezer — это парсерный стек, вдохновлённый tree-sitter, но изначально ориентированный на JS/браузер и CodeMirror 6.​

Ключевые моменты:

Инкрементальный парсер, компактные грамматики и очень маленький размер рантайма/дерева, что важно для web‑кейсов.​

Весь стек ориентирован на JavaScript/TypeScript, что удобно, если вы делаете редактор или IDE‑подобный UI в web, но менее удобно, если хотите C‑библиотеку «как у tree-sitter» для встраивания куда угодно.​

Есть утилита import-tree-sitter, которая помогает конвертировать grammars tree-sitter в Lezer (частично; многие вещи всё равно нужно править руками).​

То есть Lezer — это самая концептуально близкая «современная альтернатива», но с другим технологическим центром тяжести (JS/web вместо C/всё что угодно).

ANTLR и классические генераторы
ANTLR остаётся очень популярным генератором парсеров с кучей примеров и tooling’ом, но из коробки он не так заточен под инкрементальный парсинг на каждое нажатие клавиши.​

Его чаще используют для компиляторов, анализаторов, трансляторов, где полная прогонка грамматики по файлу — ок, а не для живого IDE‑опыта «как в tree-sitter». Для инкрементальности обычно пишут свой слой (репарсинг по регионам, кэширование поддеревьев и т.д.).​

Если нужен чисто «industrial strength» парсер под один‑два языка (типа собственного DSL или SQL‑подмножества), ANTLR может быть приятнее по экосистеме и tooling, чем пытаться допинать устаревшую грамматику под tree-sitter.

Для JS/TS в MCP-сервере сейчас логичнее опираться не на tree-sitter, а на официальный стек TypeScript (tsserver + Compiler API): он даёт полноценный AST, типизацию и уже заточен под инкрементальную работу и rich‑analysis.​

Базовый выбор: TypeScript Compiler API
Compiler API даёт полноценный AST через ts.createSourceFile, а также типовую модель через ts.Program/ts.TypeChecker, из которой можно доставать всё для анализа: типы, символы, референсы, diagnostics и т.д.​

Сам TypeScript уже реализует инкрементальность (watch/builder API, createSemanticDiagnosticsBuilderProgram и т.п.), так что можно держать долговживущий Program и обновлять только изменённые файлы, что хорошо ложится на MCP‑модель с длительной сессией.​

Для чистого AST‑анализа (без типов) достаточно парсить в SourceFile и обходить дерево ts.forEachChild, для семантического анализа — держать Program и TypeChecker.​

Обернуть готовый tsserver / typescript-language-server:

TypeScript поставляет tsserver, который использует тот же Compiler API и отдаёт все «IDE-фичи» через свой протокол.​

Существующие LSP’ы (typescript-language-server, vtsls) поверх tsserver уже реализуют большую часть логики, их можно либо:

запускать как отдельный процесс и делать адаптер MCP↔LSP,

либо использовать как reference для своей интеграции.​

В MCP‑контексте обычно удобнее иметь «тонкий» адаптер к tsserver/LSP, а тяжёлую инкрементальность и кеширование оставить TypeScript’у.

Почему не tree-sitter/Lezer для JS/TS
Tree-sitter хорошо даёт синтаксический AST, но для богатого анализа JS/TS всё равно придётся где‑то брать типы, резолвинг модулей, JSDoc и т.д.; TypeScript уже решает все эти задачи и обладает battle‑tested инкрементальностью.​

Для JS/TS TypeScript-команда сама использует Compiler API/tsserver для VS Code и других клиентов — фактически это «канонический» способ получить AST+семантику, который гарантированно будет актуальным к языку.​

Если расскажете, какие именно фичи анализа нужны MCP‑сервису (линтинг‑подобные правила, рефакторинги, кодоген, навигация и т.п.), можно предложить более конкретную схему: что держать в памяти (AST vs Program), как сериализовать деревья и как организовать incremental‑update протокол.
